# Smart-X IoT Mesh Ecosystem

## Overview

Smart-X is a hybrid IoT monitoring ecosystem designed for distributed environments such as hydroponic farms, automated real-estate utility tracking, and smart-grid environments.

The system simulates and manages telemetry generated by large numbers of ESP32-based devices. It supports heterogeneous telemetry data including environmental measurements, power-consumption measurements, and actuator states.

The application consists of two main projects:

* **SmartX.Api** — ASP.NET Core Web API backend.
* **SmartX.Client** — Blazor WebAssembly client interface.

The backend is responsible for sensor registration, telemetry generation, anomaly detection, alerts, file uploads, and data processing. The client provides the dashboard and user interface for interacting with the system.

# Generating Mock IoT Telemetry

Smart-X includes a mock telemetry generator that simulates a large number of ESP32 devices.

The default demonstration configuration generates:

* 1,000 simulated devices
* 10 readings per device
* Temperature readings
* Power readings
* Actuator/valve readings

This produces approximately:

```text
1,000 × 10 × 3 = 30,000 telemetry records
```

The telemetry generator can be triggered through:

```http
POST http://localhost:5032/api/telemetry/generate
```

The default parameters are:

```text
devices = 1000
readingsPerDevice = 10
```

Custom values can also be supplied:

```http
POST http://localhost:5032/api/telemetry/generate?devices=500&readingsPerDevice=20
```

The API validates these values before processing the request.

# Client API Connection

The client API connection is configured in:

```text
SmartX.Client/Program.cs
```

The API base address should be:

```csharp
BaseAddress = new Uri("http://localhost:5032/")
```

This allows the Blazor WebAssembly application to communicate with the Smart-X backend.

If the API is moved to another port or host, this address must be updated accordingly.

# Anomaly Detection

Smart-X monitors incoming telemetry for abnormal values.

## Temperature Anomalies

Temperature readings are checked against configured minimum and maximum values.

Readings outside the accepted range generate alerts.

Very high temperature values can be classified as critical.

## Power Anomalies

Power readings are checked against a maximum threshold.

Large power spikes generate alerts, with extremely high readings being classified as critical.

## Sensor Disconnections

The simulation also generates sensor-disconnection events.

These events create critical alerts indicating that telemetry is no longer being received from the affected simulated device.

# Generic Telemetry Packets

Smart-X uses the generic:

```csharp
TelemetryPacket<T>
```

structure to support different telemetry types.

Examples include:

```csharp
TelemetryPacket<float>
TelemetryPacket<int>
TelemetryPacket<bool>
```

This allows heterogeneous IoT telemetry to be represented using a reusable generic structure while maintaining strong typing.

---

# Sensor Value Operator Overloading

Smart-X includes a `SensorValue` structure that overloads mathematical operators.

Supported operations include:

```text
+
-
*
```

The implementation also validates measurement units before values are combined.

For example, two temperature measurements can be subtracted to calculate a temperature delta.

This demonstrates object-oriented programming and type-safe telemetry calculations.

---

# Historical Telemetry Arrays

The mock telemetry system demonstrates the use of both jagged and multidimensional arrays for historical telemetry.

Examples include:

```csharp
float[][]
```

and:

```csharp
float[,]
```

These structures represent sequential raw telemetry batches before the information is transferred into collection-based structures.

---

# Recursive Deployment Validation

Smart-X includes recursive validation for hierarchical deployment structures.

Deployment locations can contain multiple levels of nested nodes.

For example, a facility can contain zones, while zones can contain sub-zones.

The deployment validator recursively checks each deployment node and reports unconfigured locations.

This allows the validation process to work with deployment structures of different depths.

# Troubleshooting

## API does not start

Check that port `5032` is not already being used by another application.

The expected API address is:

```text
http://localhost:5032
```

Stop any existing Smart-X API processes before starting a new instance if necessary.

---

## Dashboard displays an error while loading

Confirm that the backend API is running.

Open:

```text
http://localhost:5032/api/Sensor
```

If the API is running correctly, the endpoint should return JSON.

Also check:

```text
SmartX.Client/Program.cs
```

and verify that the API address is:

```csharp
BaseAddress = new Uri("http://localhost:5032/")
```

---

## HTTPS redirection warning

The current local configuration uses HTTP.

The API should not attempt to redirect HTTP requests to HTTPS during local development.

If the following warning appears:

```text
Failed to determine the https port for redirect.
```

check `SmartX.Api/Program.cs`.

The following middleware should be disabled for the current HTTP-only development configuration:

```csharp
app.UseHttpsRedirection();
```

---

## Client cannot connect to the API

Check the following:

1. `SmartX.Api` is running.
2. The API is listening on port `5032`.
3. `SmartX.Client` is using `http://localhost:5032/`.
4. The API CORS policy is enabled.
5. The solution has been rebuilt after configuration changes.

---

## Visual Studio debugger error

If Visual Studio displays:

```text
Failed to launch debug adapter
```

or:

```text
Could not find any debuggable target
```

restart the debugging session.

A clean rebuild can also be performed:

```text
Stop debugging
```

Then select:

**Build → Clean Solution**

followed by:

**Build → Rebuild Solution**

After rebuilding, start both projects again.

Temporary localhost debugging ports created by Visual Studio should not be used as the Smart-X API address.

# Architecture

Smart-X uses a client/API architecture.

The Blazor WebAssembly client communicates with the ASP.NET Core Web API using HTTP requests.

The API processes sensor information and telemetry before returning the required data to the client.

The general communication flow is:

**ESP32/Microcontroller Simulation → Smart-X API → Telemetry Processing → Anomaly Detection → Alerts → Blazor Dashboard**

This separation allows the frontend and backend to be developed and tested independently while communicating through defined API endpoints.
